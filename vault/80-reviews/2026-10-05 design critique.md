# Design critique, 2026-10-05 (three reviewers: algorithm, methodology, systems) — verbatim findings

Source: workflow itrea-design-critique (3 agents, Claude Code subagents), 2026-10-05 23:0x–23:2x. Response and status per finding: [[2026-10-05 design critique — response]].

===== algorithm
VERDICT: Not ready for confirmatory runs. ranks.three_rank_survival does what the vault spec text says, but the spec as written cannot test the two pre-registered rank hypotheses.

- **H4 (x):** the cap on super-optimal infeasible individuals is not enforced. With few feasible individuals, the regime where the hardest instances sit, the R3 infeasible fill admits about 3x the cap, so x=0 vs x=0.1 is confounded.
- **H5 (y):** R3 keeps feasible individuals by plain key truncation. That already protects the best ones, so y=0 and y=0.2 produce identical survivor sets (200/200 random trials).
- **Lineage metric:** the ancestry bitmask saturates (all children carry an R2 bit at depth 5 under neutral selection). The pre-registered baseline "R2's share of parents" is the wrong null and biases the result toward H4.

All three need fixing, together with the D-002 wording, before E2/E3.

On operators, the defaults are likely to fail on exactly the feasibility-limited instances the study targets:
- Repair cannot hold an objective cutoff, so repairing an R2 descendant throws away the better objective that put its parent in R2.
- Mutation scales with |I|: about 1,175 genes on rail01 against at most 50 repair moves per generation.
- Uniform p_swap=0.5 crossover destroys set-partitioning rows.
- Treating continuous variables as genes cannot satisfy equality-coupled continuous variables (unit commitment, markshare slacks) to 1e-6.
- Each repair step recomputes over all non-zeros for every individual, so the planned faster kernel belongs in E0/E1, not later.

Evaluation numerics are correct for infinite bounds and equality rows in float64, and CuPy matches NumPy within 3e-14. float32 rounds the cost vector, which breaks imp_tol and post_min_gain. Non-finite vectors can reach R2.

[major] repair: objective handling (what makes R2 meaningful) — /home/coulson/git_repositories/i-trea-ii/src/itrea/config.py line 76 (RepairCfg.obj_weight=1e-4); vault/10-design/I-TREA II algorithm.md step 5
  ISSUE: The local search minimises violation plus 1e-4 * an unnormalised objective change. Repairing a child of an R2 parent therefore trades objective for feasibility and lands at a feasible point worse than inc, so the super-optimality that put the parent in R2 is lost before the child is evaluated. The unnormalised weight also misbehaves by instance: on unit-commitment costs (1e3-1e6 per unit against row-norm-scaled violations of about 1) the objective term dominates and pushes toward zero dispatch, which is infeasible. On tiny-cost instances it is ignored.
  EVIDENCE: config.py: `obj_weight: float = 1e-4  # weight of the objective change relative to the violation change`. evaluate.py normalises rows by ||A_i||_2, but nothing normalises c.
  CHANGE: Add `repair.objective_mode: cutoff_row | weighted | none`, default cutoff_row. Once inc is finite, append the row cmin·x <= inc - delta to the FJ row set with its own adaptive weight, bumped like any other row. Set delta = max(imp_tol*max(1,|inc|), g), where g is the objective granularity when every cost sits on an integer variable with integer coefficients (SCIP's objective-integrality cutoff). In `weighted` mode, scale the objective by 1/max|c_j|. Refresh the cutoff whenever inc improves; the same row also implements r2_dual_prune cheaply.

[major] repair throughput, mutation scale (make-or-break on hard instances) — /home/coulson/git_repositories/i-trea-ii/src/itrea/config.py lines 63-64, 74-75 (mutation.rate=0.01, repair.steps=50, moves_per_step=1); vault/10-design step 4-5; D-001 'RawKernel ... planned optimisation'
  ISSUE: Mutation disturbs a fixed share of |I|, while repair can make at most steps*moves_per_step = 50 single-variable moves per child per generation, each step recomputing O(nnz*P). On large set-partitioning and covering instances a child cannot be repaired within its generation, and the next generation's crossover and mutation undo the progress. General integers move only ±1 (no FJ jump values). Hard instances in the pool are feasibility-limited, and cuOpt's GPU primal heuristics are the pre-registered bar (H1). If E1 runs the vectorised version and fails its gate, that tests this implementation, not the method.
  EVIDENCE: rail01 (MPS scan): m=46,843 rows (45,509 equalities), n=117,527 binaries, nnz 392,086 → mutation 1 % ≈ 1,175 genes per child vs ≤ 50 repair moves per generation. One step touches nnz*P = 1.0e8 entries. With about 5 float64 passes that is about 4 GB of traffic, so ≥ 15 ms/step at the nominal 273 GB/s (shared with two LLM servers): a 50-step generation takes ≥ 0.75 s, and a lineage gets ≤ about 20k moves in 300 s. supportcase22 (2.2M nnz): one nnz×P float64 array is 4.5 GB, above the 4 GB pool. markshare2 (60 ints): 0.01*60 → min 1 gene, so the same parameter means 1 gene there and 1,175 on rail
  CHANGE: (1) Make mutation absolute: `mutation.genes: 4` (Poisson mean), capped at repair_moves/10; keep `rate` as an option. (2) FJ jump values for general integers and continuous variables: candidate values are the per-row tightening thresholds of the variable's rows, rounded, plus the bounds, plus ±1. (3) Incremental activity updates: only the rows in the moved column's CSC slice. Score only variables of a sample of ≤ k violated rows per individual, not all nnz. (4) Apply many non-conflicting moves per step (moves on disjoint rows). (5) Run each child's FJ to a stall criterion (no weighted-violation decrease in s steps) instead of a fixed 50 steps, using a persistent batch that refills finished lanes with new children. (6) Move the incremental/RawKernel FJ into E0/E1 and add an E1 gate: moves/s and time to first feasible against a single-core CPU FJ reference on the tuning set, measured before the 'feasible on ≥ half where SCIP does' gate is interpreted.

[major] crossover defaults for structured MIPs — /home/coulson/git_repositories/i-trea-ii/src/itrea/config.py lines 54-58 (CrossoverCfg weights uniform 0.5 / block 0.3 / k_point 0.2, p_swap 0.5)
  ISSUE: Uniform crossover at p_swap=0.5 between distant parents gives a child that is random on every disagreeing gene. On set partitioning (rail01: 45,509 equality rows; chromaticindex1024-7: 18,431 equalities) almost every disagreeing row ends up over- or under-covered.   CHANGE: Add an `agreement` operator: the child keeps genes where the parents agree, and FJ repair is restricted to the disagreement set. Make it the default, with weights {agreement: 0.6, uniform: 0.2 (p_swap 0.1), block: 0.2}. Drop k_point from the defaults (keep it as an option). Let block take the full row-closure of the chosen rows' variables, or restrict repair to the touched rows. Record per-operator success (offspring that enter R1, or posts) so E4 can tune the weights; consider adaptive operator selection as an exploratory arm.

[major] continuous variables — /home/coulson/git_repositories/i-trea-ii/src/itrea/config.py lines 77-79 (continuous='gene', lp_decode_per_gen=4, lp_time_limit=2.0); vault/10-design step 6
  ISSUE: In 'gene' mode, equality-coupled continuous variables (unit-commitment power balance and ramping, markshare slacks) will almost never reach 1e-6 relative feasibility by single-variable moves, and binary flips are scored before the slack can absorb them, so the search never sees objective gains. ===== methodology
VERDICT: D-002 is not ready for E2. Five problems have to be fixed before any confirmatory run. (1) H5 cannot detect anything with the code as written: changing y never changes which individuals survive. (2) Selecting the pool from the hardness CSV as it stands biases H1 and H2. (3) The EA gets up to 30 s of root-LP work outside the clock. (4) With about 20 instances and Holm correction over five hypotheses, only effects as large as the whole cuOpt race effect can be detected, yet the plan reads a non-significant H1 as a negative result. (5) Nothing is frozen yet: the repo has no commits, and the pool, pool-select and analysis code do not exist. Work that can start now: E0, E1 on the tuning set, and a SCIP-only screening pass that produces the frozen pool. That pass runs on the CPU only but still needs a box-window lease, because with both LLM servers up only about 20 GB is free. Proposed pool: 32 test instances × 2 fresh seeds plus 16 tuning instances, with quotas per stratum. That is about 2–3 nights of GPU arms out of roughly 100 GPU runs per 10-hour night, and about 5–6 nights in total including tuning and a rerun reserve.
