## Resolutions that changed the protocol (D-002 v3.1)
- Screening runs on 9 lanes: 10 × 9 GiB + the 20 GB reserve exceeds the ~109 GB free (screening-F2).
- Stage 2 always for PGLib-UC and ML4CO: their stage-1 reference is the run's own best (screening-F5).
- MIPLIB screening P uses the published `.solu` value (screening-F1 / analysis-F1 — the reference was resolved by job set name).
- PGLib split by base case; ML4CO list pinned; memory-fit rule = the EA's memory plan; tuning-side family cap;
  P-degenerate definition (≥ 5 % of [0, T] across zero) and exclusion from the P strata; solver-limit stops flagged.
- Screening cannot run unfrozen: `prereg-v1` is required with no bypass (screening-F4).
- Rank 1 protection ratchet (engine-F1); feasibility phase without generational replacement (engine-F4); the EA
  stops inside a generation at the budget (engine-F3); rejected incumbents revert (engine-F6, F7).
- Runner: orphans killed on resume, gates re-checked together before launch, killed-by-runner partners not
  counted as failures, toy-only exemptions, `--who` fixed, serving gate fails closed, GPU-health sparse coverage voids.
- The 07:30 restore of the LLM servers now alerts on failure (timer re-created with OnFailure) and waits for the
  runner lock.

  give each run a private CuPy kernel cache seeded from the master cache, re-measure the local-search bench with CUB
  off on large shapes; D-002 v3.1 already voids a block on `compiled_on_clock`.
- `build_runs.crash_flags` must honour `stopped_by_runner` (cuOpt killed after SCIP proves optimality is not a crash).
- `references freeze` command (step 4) — `freeze_references` has no caller yet.
- A0* emphasis job builder and the `configs/frozen-e2-solver.json` writer (E4).
- Named systemd units with `--collect`; CUDA out-of-memory classification (D-002 §6 counts it as a crash for now).
- `Trace format and metrics.md`: document the new runs.parquet columns (pt_mf, sign_crossing_*_share, n_inc_bad_t,
  pre_t0, checker_version, …).
- **Design question for Berk:** an incumbent the solver rejects is demoted, but its key still beats the incumbent,
  so at the next survival it is an infeasible-good (Rank 0) candidate — is that wanted (it is "almost feasible and
  better") or should solver-rejected vectors be barred from Rank 0?
